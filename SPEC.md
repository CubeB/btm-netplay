# Netplay: behavioural specification

This document describes, as behaviour, a peer-to-peer lockstep multiplayer
stack for a 30 Hz real-time strategy simulation: the lockstep itself, NAT
traversal by invite code, the lobby, desync detection, surviving and
re-admitting lost players, a network diagnostics overlay and chat. It is
written so that a new implementation can be built from it without reference
to any existing code. It is **not** a wire specification for compatibility
with any existing program: encodings are free to change. Where a property of
the wire matters for correctness it is marked **[required]**; where it is a
choice that merely worked it is marked **[incidental]**.

Constants are given as measured from a working implementation. Where that
implementation has a gap or a bug, section 10 says so.

Terms used throughout:

- **Peer**: one machine running the simulation. Each human player is one peer.
- **Player id / seat**: an integer 0..9 identifying a player slot. The lobby's
  seat index *is* the player id the simulation and the network use.
- **Tick**: one simulation step. Tick numbers start at 1 for the first step
  run; "scene time" is the count of ticks run so far (0 before the first).
- **Command set**: everything one player issued for one tick, possibly empty.
- **Host**: the peer that created the lobby. After the game starts the host
  has no special network role except as described for drops (section 5).

## 1. Lockstep model

### 1.1 Clock

- Nominal rate 30 ticks per second. The per-tick budget is an integer
  **33 ms** (1000/30 truncated), so a machine running "flat out at 1x" actually
  runs about 30.3 ticks per second. **[incidental]** — any fixed budget works,
  but every peer must use the same one, because peers project each other's
  progress with it (1.6).
- The game speed is a per-mille multiplier (1000 = 1x). Wall-clock time
  elapsed each frame is multiplied by the *effective* speed (1.7) and added to
  a time accumulator; ticks are paid for out of it.

### 1.2 Command sets and their numbering

- Every player contributes exactly one command set per tick, which may be empty.
  A set is an ordered list of commands (unit orders, stop, fire/move state,
  build-queue changes, self-destruct, resource sharing, game-speed change,
  and the two control commands "player dropped" and "player rejoined").
- Each player's stream of sets is numbered from 0 with no gaps. **Set number
  k is the one the simulation consumes on tick k+1.** Neither the network nor
  the simulation ever skips a number. **[required]** — the drop and rejoin
  machinery (section 5) works purely by arithmetic on these numbers.
- One set must fit comfortably in a datagram: a cap of **1000 bytes** encoded.
  If a player's pending commands exceed that (for example an order to a hundred
  selected units), the first commands that fit form this tick's set and the rest
  wait, in order, for following ticks. At least one command always goes, even if
  alone it exceeds the cap. **[required in spirit]**: a set is never split across
  datagrams, so it must be bounded.
- Each tick, the sets of all players are applied in a **fixed order: highest
  player id first**. **[required]** — any fixed order works, but it must not
  depend on hash-table iteration or arrival order, and recordings depend on it
  never changing.

### 1.3 What a peer waits for before running a tick

A tick may run only when **every player who has not been dropped has at least
one set buffered**. Then one set per player is taken and applied; a dropped
player contributes an empty set.

Kinds of player and how their sets arrive:

| Player kind | Where its sets come from | Delay |
|---|---|---|
| The local human, in a game with remote peers | Queued locally *and* sent to every peer, ahead of time (1.4) | Order delay, 1.4 |
| The local human, in a game with no remote peers | Fed one set at the moment the tick is about to run | None |
| A remote human | Received from that peer | — |
| A computer player | Generated by every peer's own copy of the AI; **never sent over the network** | Fixed depth of **7** sets, identical on every peer |

Computer-player sets are generated only on a tick that is actually about to run
(never on an attempt that is blocked waiting for a remote peer), so that a
network stall on one machine cannot shift when an AI order lands. **[required]**

### 1.4 Input delay ("order delay")

Each peer keeps its own human's buffer at a target depth D (in sets), computed
continually from the worst peer link:

```
D = floor( min( rtt/2 + 4*dev + 10 + 50 , 2700 ) / 33 ) + 1
```

where `rtt` is the largest smoothed round-trip time to any peer (ms), `dev` the
largest smoothed round-trip deviation (ms) — both defined in 8.4 — `10 ms` is an
allowance for the send rate limiter, `50 ms` an allowance for the ±3-tick drift
the clock tolerates (1.6), and 2700 ms a ceiling. On a LAN this gives 2 ticks.

Behaviour that maintains the depth, each frame **before** ticks are run:

1. If the buffered count is ≤ D, push one set built from the human's pending
   commands (possibly empty). Also push it when the game is currently stalled
   **and** there are pending commands, even if the buffer is already deep: a
   stalled game cannot drain the buffer, and a drop command (section 5) must be
   able to leave.
2. Then push empty sets until the buffer holds D.

And **after every tick that ran**, top the buffer up to D again with sets built
from pending commands. This keeps one set per tick flowing however many ticks a
single frame dispatches; without it a slow frame runs the local buffer dry and
the peer stalls on its own input.

Every set pushed locally is, in the same step, appended to the outgoing stream
for every peer. The depth only changes how long an order waits; every peer still
sees exactly the stream that was sent, so a varying D is safe. **[required]**

### 1.5 Stalls

- A **stall** is the period during which a tick is due (the accumulator can pay
  for it) but cannot run because some player's buffer is empty.
- A stall shorter than one tick budget (33 ms) is a late packet and is *not*
  counted as a stall in statistics, but is still recorded as stalled time.
- While stalled the peer keeps rendering, keeps the UI live, keeps exchanging
  packets and keeps chat working (section 7). The simulation does not advance.
- After a stall has lasted **1 s**, a centred caption appears: "WAITING FOR
  <names>", and under it the drop countdown if one is running (section 5).
- Each frame the peer reports in its packets whether its last tick attempt was
  blocked ("stalled"), so others can stop projecting its clock forward (1.6).
- The log records one line per stall, not one per frame.

### 1.6 Keeping peers' clocks level (drift gate)

Peers do not run in strict tick-for-tick step beyond the command dependency;
instead each nudges its own pace toward the group average.

1. Each packet carries the sender's current scene time, its speed, and whether
   it is paused or stalled.
2. On receipt, the receiver estimates the sender's scene time *at the moment of
   receipt* as the reported value plus the ticks that fit in half the smoothed
   RTT.
3. When estimating "now", that estimate is projected forward by elapsed
   wall-clock time × the sender's reported speed, in 33 ms ticks; a peer that
   reported paused or stalled is not projected forward at all.
4. The **average scene time** is the arithmetic mean of the local scene time
   and every remote peer's projected time (integer division).
5. The tick cost for this frame is `33 ms / g`, rounded, where
   `g = clamp(1 + 0.03 × (average − local), 0.75, 1.25)`. A peer ahead of the
   average pays more per tick and so runs fewer; one behind catches up. Nine
   ticks of lead or lag reach the clamp.
6. At most **10 ticks** run per frame. Time owed beyond that is discarded and
   counted as "lost to cap".

Peers are therefore normally within ±3 ticks of each other.

### 1.7 Speed governor (slow machines)

- After each frame a peer estimates the speed its machine can sustain, in
  per mille, as the lower of: (chosen speed × ticks dispatched ÷ ticks owed,
  counting ticks lost to the cap only if the previous frame also lost some) and
  (33 ms ÷ average cost of a tick, with the average an exponential moving
  average, α = 0.1), never above the chosen speed and never below **100‰**.
- That figure is sent in every packet.
- Every peer computes the **effective speed** = min(chosen speed, own capacity,
  every peer's reported capacity). A fall takes effect at once; a rise is
  rate-limited to **+100‰ per second**, except that raising the chosen speed
  takes effect at once if capacity allows. Every peer computes the same answer
  from the same reports, so it never needs to be a command. **[incidental]**
- While the effective speed is below the chosen speed because of named peers,
  the centred caption reads "SLOWED FOR <names>".

### 1.8 Pause and speed

- **Game speed** changes are ordinary commands in the issuing player's set and
  so take effect on the same tick everywhere.
- **Pause** is a shared value carried out-of-band in every packet, because
  while paused no ticks run and so no sets would carry it. The value is
  (revision number, issuing player, paused flag). A toggle produces revision+1
  issued by the local player. A peer adopts an incoming value only if
  (revision, player) is lexicographically greater than what it has; revision 0
  means "none". It is repeated in every packet until superseded. This orders
  simultaneous toggles deterministically and ignores stale/reordered ones.
  **[required: idempotent, order-insensitive]**

### 1.9 Things every peer must agree before tick 1

Identical program build, identical game data (mods, map bytes), identical
lobby options (line of sight, start positions, commander rule, mapping,
difficulty, ruleset variants), identical seat table (sides, colours, teams,
starting resources, AI personalities), identical **player names** for human
seats (the simulation's random seed is derived from them), and the same random
seed. Section 3 is how the lobby ensures this.

## 2. Invite codes and NAT traversal

This path exists for two players on different networks, each behind a home
router and/or carrier-grade NAT (4G/5G/satellite), with no server of our own.
Public STUN servers tell each machine its outside address; humans carry the
addresses between machines as short codes; then both sides send to each other
so their routers admit the other's traffic.

It runs only on demand (host types `/invite`, or a guest enters a code). A LAN
game never starts any of it.

### 2.1 Sockets and ports

| Socket | Default port | Used for |
|---|---|---|
| Discovery / lobby | UDP **1338** | Lobby announcements, probes, seat claims, lobby chat, and STUN queries about itself |
| Game | UDP **1337** (in-game lobby; configurable) | Punch datagrams during the lobby, then the load handshake, then the lockstep |

The external launcher (3.9) instead gives each peer game port **6670 + seat
index**.

While the lobby is up and traversal is active, the traversal component binds
the game port itself (no address-reuse option, so a port already in use is
reported rather than shared) and sends from it. When the game starts, that
socket is **closed immediately before** the game binds the same port, so that
the game's first datagrams leave from the same local port and the router reuses
the mapping. **[required for NAT]**

### 2.2 The invite code

- Carries one IPv4 address and UDP port: the **discovery socket's** outside
  address as STUN saw it (not the game port).
- Payload: 8 bytes = 1 byte version/flags (high nibble = version **1**, low
  nibble 0), 4 bytes IPv4 address, 2 bytes port (big-endian), 1 byte check.
- Check: CRC-8, polynomial 0x07, initial value 0, no reflection, no final XOR,
  over the first 7 bytes. It catches every single-character slip.
- Text: the 64 bits are written 5 bits at a time from the most significant end
  in **Crockford base32** (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, i.e. no
  I, L, O, U), giving **13 characters**; the last character carries 4 data bits
  and one zero padding bit.
- Display: a 3-letter product prefix, then groups of 4-4-5:
  `PFX-XXXX-XXXX-XXXXX`. (Choose your own prefix.)
- Reading is forgiving: case-insensitive; separators `-`, space, `_`, `.`, tab,
  CR, LF ignored; O read as 0, I and L read as 1; the prefix may be omitted;
  input longer than 64 characters is refused. Refuse if: wrong length, a
  non-alphabet character, the padding bit is 1, version ≠ 1, check mismatch,
  port 0, address unspecified or multicast.
- **No expiry and no nonce.** A code is valid as long as the address it names
  is; in practice addresses change every session, so codes are single-use.
  It is not secret and not signed.
- The same format is used for the guest's **reply code** (2.6).
- Codes are copied to the clipboard automatically when produced.

### 2.3 STUN usage (RFC 5389 Binding only)

- Servers, all queried: `stun.l.google.com:19302`, `stun1.l.google.com:19302`,
  `stun.cloudflare.com:3478`, `stun.sipgate.net:3478`. Overridable for tests.
  Names are resolved to IPv4 off the UI thread; unresolvable ones are skipped;
  if none resolve, traversal fails ("Cannot look up the address servers; is
  there an internet connection?").
- Request: a bare 20-byte Binding request with a random 96-bit transaction id.
- Response accepted only if: it is a Binding success response, the transaction
  id matches one this probe sent, **and** it came from the server it was sent
  to. Prefer XOR-MAPPED-ADDRESS, fall back to MAPPED-ADDRESS. IPv4 only.
  Reject unsendable addresses. Bounds-check everything (arbitrary bytes from
  strangers). A cheap shape test (top two bits zero, magic cookie, length field
  equal to the rest) decides whether a datagram arriving on a shared socket is
  offered to the STUN parser at all.
- **One probe per socket**, sent *from that socket*: one for the discovery
  socket, one for the game socket. Each probe:
  - sends to **all** servers at once;
  - every **250 ms** re-sends to servers that have not answered;
  - is **settled** when all have answered, or **1000 ms** after the first
    answer;
  - **times out** at **4000 ms**: settled if anything answered, failed if not.
- Choosing the public endpoint: the (address, port) reported by the most
  servers; ties go to the earliest server in the list.
- Mapping classification (per socket): if at least two servers answered and
  all answers are equal → endpoint-independent (good). If any two answers
  differ (address or port) → endpoint-dependent ("symmetric"). Fewer than two
  answers → unknown (treated as OK).

Traversal status is one of: idle, working, ready (both sockets' outside
addresses known), failed with a sentence. Failure reasons, in precedence order:
game port could not be bound; no server answered either socket; either socket
endpoint-dependent.

### 2.4 Keepalive and address drift

- Every **4 s** after settling, both probes re-ask every server that answered
  before (new transaction ids). This keeps both router mappings alive (carrier
  NATs drop idle mappings in ~10 s) and detects a moved mapping.
- While a refresh is outstanding, servers awaiting a refresh answer are left out
  of the vote if any other server's answer is current.
- If the host's discovery endpoint changes after a code was issued, the host
  room says "Your address changed. New invite code: …" and copies it. A guest's
  reply code is likewise regenerated silently and re-copied.

### 2.5 Punching

- During the lobby, every **400 ms**, the game socket sends a small fixed
  "punch" datagram to the game address of every seated remote network peer the
  lobby lists (max 16 targets). Both sides doing this concurrently is what
  opens both routers.
- Any punch datagram received on the game socket records its source (max 16).
  The host room announces "<name> is reachable directly" the first time a punch
  arrives from a seated player's IP.
- On Windows, a "connection reset" error on receive (ICMP port unreachable from
  an earlier send) is ignored.
- Lobby traffic itself also punches the discovery sockets (2.6).

### 2.6 Full sequence, two machines on different networks

```
Host                                     Guest
/invite in room chat
  -> approval required on this lobby
  -> STUN from discovery + game sockets

              --- code X carried by humans --->

                                         -> probes host discovery addr every 1 s
                                         -> STUN from its own two sockets

                                            copied, if no game appears
[if the guest's probes get through: host replies with its announcement; guest
 sees the game in the list; no reply code needed]
              <--- (fallback) code Y carried by humans ---
pastes Y in room chat (not said to room)
  -> Y's endpoint added to "announce to"
     list and pre-approved

      Waiting for that player..."

     opening the host's router
                                         guest sees game, types name, Join
                                         -> claim (with its game addr and its
                                            STUN discovery addr) every update
  "Hearing from a.b.c.d:p" (first datagram
   from that IP on discovery socket)
  seat the guest (pre-approved by Y, or
   on Accept / /accept)
  announcements carry host's game addr
Both: punch game port <-> game port every 400 ms
  "<name> is reachable directly"

```

If the reply code's address equals the host's own outside address, the host
says "That code is on this router. It joins from the LAN list." (routers rarely
hairpin).

### 2.7 Symmetric NAT

Detected by the multi-server comparison (2.3). The lobby refuses to hand out a
code and says: "This router gives each destination its own port, so direct play
cannot work." There is no workaround (no relay). Note the comparison is per
socket on one machine only; it says nothing about the other side.

### 2.8 Which address a peer is believed to be at

- A peer's address is first taken from the lobby: for a traversing peer, the
  **game address it announced**, provided that address is in the **same /16**
  (IPv4: first two octets equal; IPv6/other: identical host) as the source
  address its lobby datagrams arrived from. Otherwise: lobby source IP + the
  announced game port. The /16 tolerance exists because carrier NAT was
  measured giving one machine's two sockets different outside addresses in the
  same pool.
- **Address following** (both the load handshake and the lockstep): a datagram
  that passes the integrity check and parses, from an address not assigned to
  any peer, that names its sender's seat, where that seat's current address is
  in the same /16 as the datagram's source, **moves that seat's address to the
  source**. Logged once per move. Anything else from an unknown address is
  silently ignored. **[required for NAT]** — the router may remap ports after
  the lobby. This is not authentication.

### 2.9 Host approval flow

States for a **join request** on the host:

| State | Entered when | Leaves when |
|---|---|---|
| Pending | A claim arrives that is not pre-approved, and the lobby requires approval (host typed `/invite`) or the claim asks for it (guest came via invite code) | Accepted; claim stops being heard (expired); lobby launches |
| Approved | Host clicks **Accept** or types `/accept` (oldest pending) or `/accept <name>` (oldest whose name matches, case-insensitive) | Seated on next update if its seat is still open; dropped from list if its claim stops being heard |
| Seated | — | Leaves / removed (3.2) |

- Approval belongs to the request's random **claim token**, not the name, so
  approving "Bob" does not approve another "Bob".
- A pasted reply code pre-approves any claim whose observed source endpoint
  **or** announced STUN discovery endpoint equals the code's endpoint (full IP
  and port). No `/accept` is needed then.
- A new pending request posts "<name> wants to join. Click Accept or type
  /accept." in room chat (once); repeated claims update the same request. The
  Accept button admits the oldest. At most 10 pending requests are kept.
- `/accept` while launching: "Cannot accept a join request while the game is
  starting." With nothing pending: "No join requests are waiting." /
  "No join request from that name is waiting." On success: "Accepted <name>'s
  join request."
- Slash commands are handled locally and never sent as chat. A pasted invite
  code in the room box is likewise not said to the room.
- The host enforces approval even if the guest's claim omits the flag.
- While waiting, the guest sees the host's real roster (without itself in it)
  and the status line "Waiting for the host to accept your join request...";
  the ordinary 8-second "host did not answer" timeout does not apply while
  approval is required.
- Lobbies that never used `/invite` seat LAN guests automatically.

### 2.10 LAN discovery

- Each lobby (host) announces itself every **1000 ms**, to the IPv4 limited broadcast (255.255.255.255) and 127.0.0.1 on
  the discovery port, plus to every explicit "announce target". A change to
  the lobby is announced immediately, but at most once per **100 ms**
  (coalescing: the next send carries the latest state). Identical re-advertising
  sends nothing extra.
- Heard announcements are remembered for **3.5 s** after the last one (three
  missed = gone).
- **Probe**: a fixed short datagram sent to a typed address (IPv4, IPv6, or
  host name, optional port, default the discovery port). A machine that is
  advertising answers with its announcement, unicast, at most once per
  **250 ms** per prober (max 64 tracked probers). The game list, when given an
  address or code, probes it once per second; a joined guest keeps probing its
  host once per second, because across subnets the host only speaks when spoken
  to.
- Host names are resolved asynchronously; results cached **60 s**; failures
  retried no sooner than **5 s**; at most 8 lookups in flight. Prefer IPv4.
- An IPv4 socket handles broadcast and announcements; a separate IPv6-only
  socket on the same port handles IPv6 probes and replies. **[incidental]**
- Every source address heard (any kind of datagram) is recorded (max 32); this
  is how the host can say "Hearing from …".
- Failure to bind the discovery port is not fatal; the list is simply empty and
  says "Could not listen on this network. Press New to host a game."
- Datagrams on the discovery socket that are neither probes nor lobby messages
  are offered to the STUN probe (2.3).

## 3. Session and lobby

There are two front ends. Both end by launching every peer's game with the same
seat table; the lockstep after that is identical.

- **In-game lobby** (sections 2, 3.1–3.8): peer-to-peer over the discovery
  socket; the host is authoritative; supports LAN discovery and invite codes.
  Checks build identity, map identity, password. Does **not** check mod
  archives.
- **External launcher lobby** (3.9): a central lobby server over a reliable
  connection; checks mod archives by SHA-256; carries the rejoin protocol. Does
  **not** check build identity.

### 3.1 Lobby announcement contents (host)

A session id (16 random hex characters), map name, game port, game label, host
display name (≤ 20 bytes), password hash (optional), build identity, map
identity, setup version number ("epoch"), host's outside game address
(traversing only), launching flag, approval-required flag, up to 10 seat
descriptions, per-seat ready flags, up to 32 options (name ≤ 32 chars
`[A-Za-z0-9_]`, value ≤ 64 chars, first of a repeated name wins), and the tail
of the room chat (≤ 8 lines, ≤ 80 bytes each, each with a host-assigned
sequence number).

A seat description: index 0..9, kind (open / human-at-host / network /
computer), side, colour 0..255 (only 0..9 meaningful), team −1..9 (only −1..4
used), name, address `host:port`, starting metal and energy (each clamped to
0..1 000 000, default 1000), AI personality (≤ 32 chars), ready flag. For a
network seat the personality field carries the **claim token** of the guest
holding it, which is how a guest recognises its own seat.

The whole announcement must fit one datagram of **1400 bytes**. If it does not,
drop whole chat lines oldest first, then trailing options one at a time; if it
still does not fit, the lobby is not advertised. Unknown fields must be ignored
by readers (forward compatibility). **[required: bounded, tolerant parsing]**

Options carried: commander rule (game ends / continues / deathmatch), start
locations (fixed / random), mapping (unmapped / mapped), line of sight
(permanent / true / circular), AI difficulty (easy / medium / hard), ruleset
variant on/off (toggled by host command `/community`). A guest applying them
ignores unknown names and out-of-range values.

Names are only carried for seats a person plays, because names seed the RNG.

### 3.2 Seats: join, leave, removal

**Guest join (Join pressed on the game list).** Checks, in order, each a message
box: name entered ("You must enter your name"), a game selected ("Select a game
to join"), not launching ("That game has already started"), build compatible
("That game is version X and this is Y"), password matches ("Incorrect
password"), map present ("You do not have the map M"), map identity matches when
the host gave one ("Your copy of the map M is not the host's"), an open seat
exists ("The game is full").

Then the guest picks the **lowest-numbered open seat**, makes a random 8-hex
claim token, and repeatedly announces a **claim**: a one-seat lobby message
whose session is the host's session plus a marker and the token, carrying its
name, chosen side/colour/team, ready flag, the setup epoch it read, its game
port, its outside game address (if traversing), its STUN discovery address (if
it has a reply code), approval flag, and its last ≤ 4 chat lines. Claims go by
broadcast and also unicast to the host's source address.

**Guest claim state**, read from each host announcement:

| Host shows my seat as | Meaning |
|---|---|
| network seat with my token | Accepted |
| open | Waiting |
| anything else, or absent | Lost |

Transitions: Waiting→Accepted on first sight. Accepted→(Waiting or Lost) =
"You were removed from the game". Waiting longer than **8 s** without approval
in play = "The host did not answer". Lost before ever accepted = pick the next
open seat (with a fresh token unless approval is in play — an approved token
must survive) or "The game is full". Host announcement not heard for **5 s** =
"The host has left". Host changes to a map the guest lacks = "You do not have
the map M".

The guest mirrors the host's announcement wholesale on every update (seats,
options, map, ready flags, chat). A guest's own side/colour/team click is shown
immediately and sent in its claim; it is held for up to **2 s** or until echoed,
then the host's word wins.

**Host seating.** On each update the host:

1. Drops pending/approved requests and removed tokens whose claims are no longer
   heard.
2. Frees any seated guest whose claim is no longer heard (3.5 s expiry):
   "<name> has left".
3. For each heard claim: ignores removed tokens; refuses incompatible builds
   (says once per token: "<name> cannot join: it is version X" and "This is
   version Y"); for an already-seated token, follows a changed address, applies
   a *changed* side/colour/team choice (a colour already held by another active
   seat is refused, the seat keeps its colour), and takes ready = claimed ready
   only if the claim's epoch equals the current one (or is absent); for a new
   token, applies approval (2.9), then seats it if the requested seat is still
   open: "<name> has joined". The new seat is first given a colour no other
   active seat holds.
4. Host clicking a guest's name button removes it: "<name> was removed"; the
   token is remembered so the still-arriving claim cannot re-seat it.

Lobby chat: the host assigns each line a sequence number and keeps a transcript
(≤ 200 lines); guests append lines newer than their newest; guest lines are
taken from claims de-duplicated per guest by the guest's own sequence number.

### 3.3 Ready and setup epoch

- The host's own seat and computer seats are always ready; an open seat never.
- A **setup fingerprint** covers the map, all options, and each seat's index,
  kind, side, colour, team, resources and (for computers) personality — not
  names, addresses, tokens, ready flags or chat. When it changes, the host
  increments the epoch and clears every ready flag. A guest seeing a new epoch
  clears its own ready. A ready flag given under an older epoch is not believed.
  **[required]** — stops the host starting on a stale "ready".
- Start is blocked (with a reason on the help line) when: no map; any network
  seat not ready; nobody else in the room.

### 3.4 Build identity check

- Identity = the source revision the executable was built from (hex, ≤ 40
  chars) plus a `-d` suffix if the working tree differed; or `unknown` for a
  build made without version control. It must be regenerated **every build**
  (not at configure time). Debug/release and OS do not change it.
- Every lobby message a machine sends is stamped with it automatically.
- Compatibility rule (`mine` vs `theirs`): compatible if mine is empty or
  unknown; else **incompatible if theirs is absent** (an older build that does
  not send it); compatible if theirs is unknown; otherwise compatible iff equal.
- Enforced at both ends: the guest's list and Join refuse; the host refuses to
  seat (3.2). The host-side refusal is what protects against old builds that do
  not check.
- Display form: first 8 characters plus `-d` if dirty; "an older version" for
  absent.
- Courtesy, not authentication.

### 3.5 Map identity

`<size of map description file in hex>-<size of terrain file in hex>-<64-bit
FNV-1a over description bytes, then a 0xFF separator byte, then terrain bytes,
16 hex digits>`. Empty if unreadable. Compared on Join; absent means not
checked.

### 3.6 Password

Optional. Announced as 64-bit FNV-1a of `session + "\n" + password`, 16 lower
hex. A courtesy gate only (visible on the wire, trivially brute-forced; the game
traffic is unauthenticated anyway). Never present it to players as security.

### 3.7 Game start handshake

1. Host presses Start (allowed only if not blocked, 3.3). The host validates the
   game setup locally first, then sets the launching flag in its announcement
   for **2.5 s** and shows "Starting game...". New claims are not seated while
   launching.
2. A guest that is Accepted and sees the launching flag re-checks the map is
   loaded ("Could not load the map M" otherwise) and starts.
3. The host starts when the 2.5 s elapse. On start each machine tears down the
   lobby (stops discovery; closes the traversal socket so the game port is free)
   and builds the game from its mirrored seat table: its own seat is the local
   human, every other human seat is a remote peer at the address in the table.
4. **Load handshake** on the game port: every **100 ms** each peer sends to every
   other peer a status message (loading / ready) that names its own seat.
   A peer marks a remote "ready" on receiving ready from it, or on receiving any
   lockstep packet from it (it has already started). Address following (2.8)
   applies.
5. After loading, a peer sets its own status to ready and waits until all
   remotes are ready, timing out after **120 s** with "Timed out waiting for
   other players to finish loading (player n at host:port, …). They may have
   lost the connection, or the address may be wrong."
6. The lockstep then starts on the same port. All streams start at sequence 0;
   hash comparison starts at tick 1.

A rejoining peer (5.6) skips step 5.

### 3.8 Ten seats

Ten seats (ids 0..9) are a hard limit everywhere: lobby, launcher, simulation.
Colours 0..9. Teams: none or 0..4 in the in-game lobby.

### 3.9 External launcher lobby and mod-archive matching

A central lobby server (reliable, ordered message connection) holds rooms of 10
slots (filled / empty / closed). Messages (all inputs validated: strings
trimmed, control characters removed, bounded — name ≤ 32, chat ≤ 500, reason ≤
200, map name ≤ 128, ≤ 64 mods, ≤ 512 archives per mod; semicolons in names
replaced because names reach command lines):

| Direction | Message | Carries |
|---|---|---|
| C→S | handshake | game id, name, IPv4 address, optional admin key, installed mod names |
| S→C | handshake response | your player id, admin id, slots, map, active mods |
| C→S / S→all | chat / player chat | text / (player id, text) |
| S→all | player joined / left | id, name, mods / id, new admin id |
| C→S / S→all | ready / player ready | bool / (id, bool) |
| C→S / S→all | change side, team, colour / player changed … | value / (id, value) |
| C→S / S→all | open/close slot / slot opened/closed | slot id |
| C→S / S→all | change map / map changed | name |
| C→S / S→all | set active mods / active mods changed | names |
| C→S / S→all | set archives / player archives changed | per mod: archive (name, size, SHA-256 hex) list, optional manifest (size, SHA-256, optional entry script path/size/SHA-256) |
| C→S | request start | — |
| S→all | start game | (player id → address) list |
| S→all | start refused | message |
| Rejoin messages | see 5.6 | |

Archive fingerprints are sent separately after the handshake because hashing
gigabytes takes time; a player is "unchecked" until they arrive.

**Start rule** (enforced by the server, also used by the client to grey Start):
only the admin may start ("Cannot start: only the host can start the game.");
a map must be chosen ("Cannot start: choose a map first."); then all of: no
empty slots, everyone ready, everyone has all active mods installed, reported in
one message "Cannot start: some player slots are still open; waiting for A, B to
ready up; C do not have all of the active mods." Then archive agreement: each
player is compared to the admin (or first player with fingerprints) for each
**active** mod only. Archive names compared case-insensitively; a difference is
missing / extra / different hash; manifest likewise (and its entry script).
Any difference refuses: "Cannot start: the players do not have the same game
data (Bob has mod/file.ext, …). Both players must use the same mods, maps and
archives." Any player whose fingerprints (or a mod's) have not arrived refuses:
"Cannot start: still checking the game data of Bob. Wait for the data check to
finish."

A 6-hex digest (SHA-256 over a canonical, load-order-sorted listing of active
mods' archive names and hashes, manifest and entry script hashes) is shown
beside each name for humans to compare; the refusal, not the label, is
authoritative.

Admin leaving passes admin to the first filled slot. Game ports are 6670 + slot
index. Every launcher-started network game records a replay (required for
rejoin). Hashes are self-reported: prevents accidents, not cheating.

## 4. Desync detection

### 4.1 What is hashed and when

- After every tick a peer runs (never on a blocked attempt, never during
  replay/rejoin catch-up), it computes a 32-bit hash of the **entire
  simulation state** — game time, every player's economy and status fields,
  every unit's simulation fields and orders, projectiles, map features,
  wind, end-of-game countdown and rules, win state, exploration grids, AI
  controller state that affects future commands, mission and mod script state
  — and both stores it locally and sends it to every remote peer.
- The first hash a peer produces is for tick 1. Hashes form a gapless ordered
  stream per peer, numbered like the command stream; **the tick a hash belongs
  to is not carried — it is implied by position.** **[required: ordered,
  gapless]**
- Only machines that run their own simulation are hash sources: the local peer
  and each remote human peer. **Computer players are not hash sources.**
  (A hash buffer that nobody fills would block comparison for everyone.)

### 4.2 Comparison

- Each peer holds a queue of received hashes per source.
- Repeatedly: if every *participating* source has a hash queued, take one from
  each and compare. A source participates from its first tick (1, or its rejoin
  tick) onward; before that it is skipped, not waited for.
- If all agree, advance the comparison tick by one. If any differ, the
  comparison tick is the **first diverging tick**: report it.
- If no source participates at the current comparison tick, jump the counter to
  the earliest first-tick of any source (rejoining peer case) or stop.
- Because every peer compares the same ordered streams, **every peer names the
  same first diverging tick**, typically noticed a round trip later.
- The result is sticky: once found it is returned forever.
- Checked at the start of every tick attempt.
- A source's queued-hash count is capped at 900 (30 s); excess is not taken and
  not acknowledged.

### 4.3 What happens

The peer writes a dump (4.4), logs and shows a fatal error box, tells the
launcher the game ended "abandoned" at that tick, and the game ends. Text:

```
Desync detected.

The simulation diverged from the other players at tick T.
This peer is player P, and noticed at tick N.

  player 0  0x1234abcd
  player 1  0x1234abce  (this peer)

A state dump for a bug report was written to:
  <path>

Every peer writes one naming the same tick. A report wants them all.
```
(or "A state dump could not be written; see the log.")

### 4.4 Dump

File `<app data dir>/<prefix>-desync-tick<T>-player<P>.json` (one per peer per
diverging tick, so they sort together). JSON object:

| Field | Meaning |
|---|---|
| `desync.firstDivergentTick` | T |
| `desync.localPlayer` | P |
| `desync.detectedAtTick` | local scene time when noticed (≥ T) |
| `desync.hashes[]` | `{player, hash}` for every participating peer at T, player order |
| `desync.build`, `desync.commit` | product version string and configure-time revision |
| `desync.buildIdentity` | the per-build identity of 3.4 (authoritative) |
| `state` | the simulation state **as hashed** (each field the hash reads, so a diff of two peers' dumps lists only candidate fields): game time, players, units, projectiles, features (+ a table mapping feature-definition indices to names), wind, countdown, rules, win state, exploration, cloak bookkeeping, optional mission/mod/AI state |

Note the state is the peer's state **at detection time N**, not at T. Writing
the dump must never throw; failure is logged.

## 5. Lost players

### 5.1 Detection

- Per peer, "silence" = time since **any** valid packet from it (a packet with
  no new commands still counts). A peer never heard is measured from when the
  lockstep transport started.
- Liveness is evaluated every frame, but a peer is considered only while the
  next tick is blocked on it (its buffer empty). A peer that is merely a little
  behind is never counted down.
- **Drop timeout: 10 s** default, configurable 0..600; **0 means never drop**
  (wait forever).

### 5.2 Countdown

While blocked on a silent peer whose silence < timeout, show "DROPPING IN n"
under "WAITING FOR …" (after the 1 s caption delay), n = whole seconds remaining
+ 1, minimum over such peers.

### 5.3 Who declares the drop, and at which tick

- Exactly **one** peer may declare a given player dropped: the **lowest-numbered
  hash-source player other than the lost one that is not itself dropped**.
  Everyone computes this from shared state, with no message. **[required]**
  (Normally the host, seat 0; but if the host is the one lost, seat 1 etc.)
- When silence ≥ timeout and this peer is the designated one (and has not
  already issued a drop for that player), it appends a **"player dropped"
  command** (player, from-tick) to **its own** pending commands. Because it is
  stalled, 1.4's stall rule lets that set out immediately.
- from-tick = max(local scene time, number of sets this peer has submitted,
  every peer's last reported scene time) + **60** ticks. The max over submitted
  sets matters when the order delay is deep.

### 5.4 Applying a drop (every peer, including the issuer)

- **On arrival** of a set containing a drop (when it is pushed into the buffer,
  not when its tick runs) — because the stalled tick cannot run until it is
  applied. Validity: issuer must be the designated declarer; from-tick ≤ ticks
  consumed so far + **900**; the player not already dropped. Invalid drops are
  stripped from the set and logged. **[required: idempotent; a second drop for
  the same player is ignored]**
- The cut: the dropped player's stream is forced to exactly from-tick − 1 real
  sets: buffered sets beyond that are discarded from the back; if fewer have
  arrived, empty sets are padded up to it. From from-tick on they contribute
  empty sets and are never waited for. If more than from-tick − 1 had already
  been *consumed*, that is an unrecoverable desync; log it (the margin exists to
  prevent it).
- They stop being a hash source. Packets from them are thereafter ignored.
- When the drop command's own tick runs: the console says "<name> has left the
  game" (once), the launcher is told (player, tick), the transport forgets the
  peer but remembers its address (for rejoin), and the waiting caption clears.
- **Units:** the simulation schedules removal for the agreed tick: at that tick
  the player is marked dead and removed from the game, and **every live unit it
  owns self-destructs** (with explosions, which can damage others). Packet
  arrival never decides when units die. **[required: tied to the agreed tick]**

### 5.5 Known gap: two simultaneous drops

The declarer rule (5.3) deadlocks when the two lowest-numbered live peers are
lost together: the declarer for the lowest is the second-lowest and vice versa,
so no surviving peer is entitled to declare either, and the survivors wait
forever ("WAITING FOR …" with no countdown). Other pairs resolve in sequence (the
first drop changes who is entitled for the second). Also unhandled: asymmetric
partitions, where two survivors disagree about who is silent; a drop issued by
one is accepted by others even though they still hear the "lost" peer, and
conflicting declarations can be accepted in different orders on different
peers. See 10.

### 5.6 Rejoin by replay fast-forward

Only available through the external launcher, and only if the peers record
replays (launcher games always do). Rejoin is a lockstep event agreed at one
named tick R; the remaining peers **stall at R** until the returning peer has
caught up and begins sending.

Roles: **returning peer** (dropped player), **speaker** (the designated declarer
for that player, 5.3), **others**, **lobby server**.

Sequence:

1. Every peer's launcher reports drops to the server; the server records the
   dropped player and broadcasts it.
2. The returning player's launcher sends "request rejoin". The server refuses
   ("your game has not reported you as dropped" / "there is nobody left in the
   game to let you back in") or forwards "rejoin requested (player)" to the
   speaker — the first filled, non-dropped lobby slot other than the requester.
3. The speaker's launcher asks its engine to rejoin that slot. The engine checks:
   the player is dropped ("that player has not been dropped"), this peer is the
   designated declarer ("this peer is not the one to speak for that player"),
   not already in progress ("that player is already on their way back"). Any
   refusal is sent back as "rejoin refused (player, reason)".
4. The speaker appends a **"player rejoined" command** (player, R = local scene
   time + **120**) to its own commands.
5. On arrival of that set on every peer (validated as for drops: issuer is the
   designated declarer, R ≤ consumed + 900): reopen the player's stream at R.
   Refuse (log, no change) if R ≤ the drop tick or R ≤ ticks already consumed.
   Pad empty sets for every tick from max(sets pushed, ticks consumed)+1 to R−1,
   set the pushed count to R−1, clear the dropped mark, and register the player
   as a hash source from tick R. From R on, the game needs their sets again.
   Idempotent.
6. When the command's tick runs on each peer: console "<name> has rejoined the
   game"; the player may be dropped again later; a **180 s grace** begins in
   which the player is not counted down or dropped for silence (ends early once
   it is heard). Once this peer's own submitted stream reaches sequence R−1, the
   transport starts sending to the remembered address again, resending its own
   sets **from sequence R−1** out of a retained history of the last **3600**
   sets (2 minutes; if it no longer holds R−1, log and stay stalled), and
   expects the returning peer's sets from sequence R−1 (anything older is
   discarded).
7. When the speaker's scene time reaches R−1, it cuts a **catch-up bundle**: a
   finished replay of the game so far (game setup header incl. seed, then every
   recorded tick's non-empty sets per player, plus an end record stating the
   last tick, R−2). It hands the file path to its launcher ("rejoin bundle
   player, tick R, file"), or refuses ("this peer is not recording a replay" /
   "the rejoin bundle could not be written").
8. The launcher sends the bytes to the server; the server checks the sender is
   the speaker, un-marks the player as dropped and relays the bundle to the
   returning player.
9. The returning player's launcher writes the file and starts the engine with
   "rejoin from this file at tick R", same players and addresses.
10. The returning engine loads, **does not wait for the load handshake**,
    registers every hash source from tick R, and starts its streams to every
    peer at sequence R−1 (send and receive, commands and hashes). It sets the
    transport to **not accept** incoming commands: arriving packets count as
    signs of life but are not taken or acknowledged (so senders keep them).
11. It winds the recording forward as fast as the machine allows (no per-frame
    tick cap: blocks of up to 2000 ticks per frame) until its scene time is R−1.
    Human sets come from the recording; computer players are re-run from their
    own AI so their internal state is rebuilt; recorded pause and speed
    commands are ignored. No hashes are sent during the wind.
12. On reaching R−1 (checked both at the top of each tick and once per frame,
    because the recording stops dispatching ticks when it runs out): set its
    submitted count to R−1, stop using the recording, start accepting
    commands, console "Rejoined the game". From here it is an ordinary peer.
13. The others, stalled at R, receive its sets and continue; hash comparison
    includes it from tick R.

If the bundle does not reach through R−2 the returning engine refuses to start
("Rejoin bundle ends at tick X but a rejoin at tick R needs it through tick Y").

## 7. Chat during stalls

- In-game chat travels **beside** the command stream, not in it, as its own
  sequenced, acknowledged, retransmitted stream per peer (8.3). It never reaches
  the simulation. It therefore works while the game is stalled or paused, which
  is exactly when players want it.
- Recipients are chosen on the sending machine: everyone, allies, enemies, or
  specific seats. A private line is **only sent to its recipients**; the label
  (none / allies / enemies) travels only to tag the display. The sender is the
  packet's sender (not carried).
- If any recipient already has **32** unacknowledged chat lines, the line is
  refused and the console says "Message not sent: a player is not answering".
  Addressed to seats that are not players: "Message not sent: no such player".
- The sender shows its own line immediately (nobody echoes).
- Received text is sanitised before use: invalid UTF-8 replaced by `?`,
  control characters removed, at most **128** code points, trimmed; empty lines
  discarded (but still consume their sequence number).
- Lines starting with the command prefix are local console commands and are
  never sent.

Lobby chat (before the game) is the separate mechanism of 3.2.

## 8. Wire protocol

### 8.1 Transport

- UDP. IPv4 and IPv6 (dual-stack socket) for the lockstep; IPv4 only for STUN
  and invite codes. **[incidental: IPv6 support]**
- Each lockstep/handshake datagram = encoded message + **4-byte CRC-32**
  (IEEE 802.3 polynomial, reflected, init 0xFFFFFFFF, final XOR 0xFFFFFFFF),
  little-endian. Datagrams shorter than 4 bytes, failing the CRC, or failing to
  parse are dropped (logged only if from a known peer). **[required: integrity
  check; CRC is not a MAC]**
- Maximum datagram 1500 bytes including the CRC; receive buffers 1500.
- No fragmentation, no separate reliability layer, no connection setup:
  reliability comes from **cumulative acknowledgement and full retransmission of
  everything unacknowledged in every packet**. Ordering is by sequence numbers.
  **[required: survive loss, duplication and reordering]**
- One packet to each peer every **100 ms** regardless (heartbeat), plus an
  immediate packet when a set, hash or chat is submitted, rate-limited to one
  per **10 ms** per peer (a deferred flush covers what the limit held back).
- A handler error on one datagram costs only that datagram; it must never stop
  the receive loop. **[required]**
- Encoding in the reference was a schema-based binary encoding with optional
  fields for forward compatibility. **[incidental]**

### 8.2 Message kinds

| Kind | Phase | Purpose |
|---|---|---|
| Load status | Load handshake | "I am loading / I am ready", sender seat |
| Lockstep update | Game | Everything else: three streams + run state |
| Punch | Lobby (game port) | Fixed short datagram, opens NAT |
| Lobby announcement / claim | Lobby (discovery port) | Text, key=value lines, see 3.1 |
| Discovery probe | Lobby | Fixed short datagram, "please announce to me" |
| STUN Binding | Lobby | RFC 5389 |

### 8.3 Lockstep update fields

| Field | Meaning | Properties |
|---|---|---|
| sender player id | who sent it | used for address following; must match the link |
| packet id | per-sender counter, logging only | incidental (deliberately not random) |
| sender scene time | for the drift gate | latest wins |
| speed ‰, paused, stalled | sender's run state | default 1000/false/false if absent |
| sustainable speed ‰ | for the speed governor | default 1000 |
| shared pause (revision, player, paused) | 1.8 | repeated every packet; merge by greater (revision, player) |
| next command seq to send | sequence number of the first set included below | |
| next command seq to receive | cumulative ack of the peer's commands | |
| command sets[] | consecutive unacked sets from the above number | idempotent; prefix of the stream |
| next hash seq to send / to receive | same scheme for hashes | |
| hashes[] | consecutive unacked 32-bit hashes | |
| next chat seq to send / to receive | same scheme for chat | |
| chat[] | (text, optional audience 0/1/2) | |
| ack delay ms | time since this sender last received a packet with new commands from the recipient | for RTT correction |

Receiver rules, for each of the three streams **[required]**:

- Ack: pop own buffered items up to the acknowledged number (ignore an ack
  beyond what was sent; log it).
- Data: if the first included number > next expected, ignore the rest of the
  packet (a gap; resend will fix it). Otherwise skip the already-received prefix
  and take the rest in order, advancing the expected number.
- For commands: decode all new sets first; if any fails to decode, take none of
  them (the sender will be dropped for silence if it persists). Stop taking (and
  so stop acknowledging) when that player already has **900** sets buffered.
- Any valid packet counts as a sign of life.

Packet assembly: include as many unacked sets as fit, then hashes, then chat
(each the longest prefix that fits, found by halving), under 1496 bytes. A single
set that cannot fit is logged and never sent (that peer will be dropped).

### 8.4 RTT

- When a packet goes out, record (sequence just past its last set, time), only if
  that sequence is new.
- When an ack arrives exactly equal to the oldest recorded sequence, RTT = now −
  that time − the peer's reported ack delay (floored at 0).
- Smoothed RTT: EMA, α = 0.1. Deviation: first sample seeds it at RTT/2; then
  dev = 0.75 dev + 0.25 |sample − smoothed| (RFC 6298 style).
- Measured in whole milliseconds (reads 0 on loopback).

### 8.5 Load status fields

status (loading / ready), sender seat. A lockstep update received during the
handshake also means "ready".

## 10. Known gaps and lessons

Each item is marked **(code)** if observed in the implementation, **(docs)** if
only stated in its documentation, or **(analysis)** if inferred by reasoning
about the code's rules.

### Not provided
1. **No relay / TURN fallback.** Symmetric NAT and UDP-blocked networks cannot
   play across the internet. (code, docs)
2. **No spectators/observers in a lockstep game.** Seat kinds are open, human,
   network, computer only. (code)
3. **No hairpin support**: two machines behind one router must use LAN
   discovery. (docs; code only warns)
4. **IPv4 only** for STUN and invite codes. (code)
5. **No peer authentication or encryption.** Peers are identified by source
   address; CRC is unkeyed; a peer's address can be "followed" anywhere in the
   same /16. The password is FNV and public. Archive hashes are self-reported.
   A dishonest peer can stall others by under-reporting its scene time, or end
   the game with a false hash. (code, docs)
6. **Rejoin only through the external launcher**, which alone records replays
   and carries the bundle; in-game-lobby games cannot be rejoined. (code)
7. **The two lobbies check different things**: in-game lobby checks build
   identity + map identity but not mod archives; launcher checks archives but
   not build identity. A new design should check both everywhere. (code)
8. **Three or more players across NATs** relies on each guest punching other
   guests at addresses the host relays; "two people is the case looked at
   hardest". (docs)
9. **Invite codes carry no expiry or session binding**; staleness is detected
   only by STUN refresh on the issuer. (code)

### Bugs and limitations seen
10. **Two simultaneous drops can hang the game forever** when they are the two
    lowest-numbered live peers (5.5). (analysis of code)
11. **Asymmetric partitions** can produce divergent drop decisions (5.5); the
    only protection is that later desync detection would end the game.
    (analysis)
12. **The sync hash is a plain 32-bit sum** of field values (floats contribute
    `value × 65536` truncated; strings sum their bytes). Swapped values cancel,
    and the implementation had to pack flags and double-count fields to avoid
    obvious collisions. Use a real order-sensitive hash (e.g. 64-bit FNV/xxHash
    over a canonical serialisation). (code)
13. The desync dump is taken at **detection** time, a round trip after the
    divergence; nothing captures the state at the diverging tick itself.
    Consider keeping a ring of recent per-tick state snapshots or field-level
    sub-hashes. (code)
14. Integer tick budget: 33 ms gives 30.3 ticks/s, not 30. (code)
15. A dropped player's units **self-destruct** (with blast damage to
    neighbours) rather than being removed silently; decide deliberately.
    (code)
16. A command set larger than one datagram is never sendable and causes its
    sender to be dropped; prevented only by the 1000-byte split. (code)
17. The rejoin history window is 3600 sets (2 min) past the agreement point;
    adequate given the 120-tick margin, but fragile if the speaker is stalled
    long before cutting. (code)
18. The rejoin "speaker" is chosen by the launcher server as the first lobby
    slot, and by the engine as the lowest player id; if those orderings ever
    differ, a rejoin request goes to a peer that will refuse it. (code)
19. A rejoining peer must come back from the same address it had (the transport
    reuses the remembered address; address following only allows a port change
    within the /16). (code)
20. Lobby announcements are lossy by design; a guest's chat is protected only by
    repeating its last 4 lines in every claim. (code)

### Code vs docs disagreements (code wins)
21. Docs say STUN servers are "tried in order and cost a second when one is
    down"; the code queries all at once. (code vs docs)
22. Docs say a game address in a lobby message is "only believed by a machine
    that is itself traversing"; in the code the **host always believes a
    guest's announced game address** (if same /16), while a guest believes the
    host's only when it joined via a code. (code vs docs)
23. Overlay docs say packets "do not yet say what speed or pause state" a peer
    is in; the code now carries speed, paused, stalled and sustainable speed.
    (code vs docs)
24. Docs list the reference's NAT design as "not verified on a real network" for
    the game-port handover; field use since reports it works on strict routers
    and carrier NAT. Treat the handover (2.1) as required. (docs; field report)

### Lessons worth keeping
- Make every control action (drop, rejoin) an **ordinary in-stream command from
  a deterministically chosen peer, naming a future tick**, applied on arrival
  but taking effect at the tick. It needs no extra agreement round.
- Keep chat and pause **out of** the command stream so they work while stalled.
- Retransmit-everything-unacked with cumulative acks is simple and survives
  loss, duplication and reordering; bound every buffer (sets, hashes, chat).
- Generate AI commands per tick on each peer, never per frame, and never on a
  blocked tick attempt.
- Stamp every lobby message with the build identity and refuse at **both** ends.
- Version every "ready" against a setup fingerprint.
- Probe NAT from the **actual sockets** that will carry the traffic, refresh
  every few seconds, and hand the game port over by close-then-rebind.
- Never let one bad datagram kill the network thread.
